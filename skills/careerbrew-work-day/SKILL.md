---
name: careerbrew-work-day
description: Runs the user's work day with careerbrew's `/work` runner. Reads the day plan (`careerbrew day run --json`), runs each step in order, keeps one status row per step (`careerbrew day update`), saves every question as a record and asks them once at the end after a recheck, keeps watching, and ends the day by clock with careerbrew's PM draft, a handoff, and the day's page (`careerbrew day end`); runs one long-lived session per pressing project (`careerbrew work session`). Use when the user says "/work", "run my work day", "start the work day", or "end of day". Don't use for planning time blocks (use careerbrew-day-planner), for the morning start alone (use careerbrew-start-session), or on a job-hunt-only day.
---

# Work day

First, load `careerbrew-best-practices` (privacy, sources, machine role, never send, measure, iterate).

careerbrew owns the work day: every work-day feature lives here because it is career work. Run careerbrew from anywhere as `careerbrew …` (the launcher `scripts/setup.sh` installs).

1. Run `careerbrew day run --json`. It reads local files only and changes nothing. Its text fields are your instructions; this skill adds only what they leave out.
2. `start_of_day`: first show the day's steps as `N. /step: <about>`, one per line (each step's `about` from `day run --json`). Then run `careerbrew day start` once, before stage 1. It fast-forwards the checkouts (never a reset; one with local work is reported, not touched), names the shell traps, and probes sign-in. Ask its sign-in question (`questions`) right away: it is the day's only sign-in ask. Give every step's subagent the traps file (`traps`) to read first, and run tests with a named interpreter (`uv run python -m ...` or `.venv/bin/python`), never bare `python3`.
3. Before the first step, tell the user in two lines: the machine (`machine`) and the steps you will run (`steps[].step`).
4. `rule`: follow it all day. Every public issue, PR, message, or comment stays a draft until the user says yes.
5. After `day start`, run `/careerbrew` inline, then each `start_of_day.operator_turn` quick dispatcher in `day check --json` readiness order inline in the main session in the owner's initial turn, before waiting on any background result. Mark `start_of_day.operator_turn_blocked` steps blocked with the existing sign-in ask; independent work may continue. Do not defer these dispatchers to a background-started turn. Use only exposed host controls; a refused dispatch becomes a blocker, never a claim that it started. Then run `careerbrew day check --json` and start the steps in `ready`, one subagent each. Mark them running before another check. Recheck when any step completes or becomes blocked; never wait for unrelated stage peers. `stages` is only an earliest-start view; `ready_when` and `why` explain dependencies and resources. A long-running step starts when its own prerequisites and resources are free and keeps running. Run each one with the Skill tool. When `user_only` is true or the Skill tool cannot load it, read the file at `path` and follow it (starting `/work` is the user's request to run it). When `path` is null, say in one line that the step is not installed here and mark its row blocked.
6. `handled_rule`: before a step works on a checkout or a PR, skip it when `handled` lists it; after the step, record what it handled with `careerbrew day update <step> --handled checkout:<path>`.
7. Rows: when a step starts, `careerbrew day update <step> --status running`. When it ends: `--status done` (or `blocked` / `failed`) with `--summary "<one line>"`, `--needs-you "<the ask>"` when it waits on the user, and `--link <url>` for its PR or page. Stop only for `stop_only_for`.
   - `truth`: a step with `verify` is done only when its verify passes; `day update --status done` exits 1 and marks the row failed when it does not. Say so in one line and go on.
   - `blocked` always takes `--needs-you` (the question); `failed` always takes `--error-class env|auth|network|conflict|tool`. Never mark a broken step blocked.
   - Run `careerbrew day check --json` before each dispatch and on each watch pass; start its ready steps. Run each step it set back for a retry again; a step it marks failed stays failed.
8. `questions`: a step never asks the user itself. It returns each question as a record and goes on: `careerbrew day question add <step> "<the ask>" --option <a> --option <b> --pick <your pick> --recheck <check>`. The recheck is a command that exits 0 while the item is still open (the draft still exists, the PR is still open), or a link you check yourself. A command must fail once the item is done, and only then: `sh -c 's=$(gh pr view 12 --json state -q .state) || exit 0; case "$s" in MERGED|CLOSED) exit 1 ;; esac'`. Not `gh pr view 12` (it exits 0 after a merge too), and not `grep -qx OPEN` (a gh that is offline or signed out would close the item). Tell every step's subagent this rule. After the last step, run `careerbrew day question recheck --json`: it runs every recheck, drops the closed items, and lists the rest with their age. Check each `agent` item's link and close a done one with `careerbrew day question close <id>`. Then ask them all in one batched ask: what each item is, its age, what each option does, and your pick. Close each item the user answers. Open records carry over to the next morning.
9. The page: run `careerbrew day render` after the last step and whenever a row starts to need the user. It prints the page path and one summary line. Show it with `careerbrew open --report work-day`. Read its items with `careerbrew report latest --run work-day --json` (ids, statuses, commands; never row text). Never publish the page: it holds the user's own data. Each ended row says how long it took; a `slow` row took more than `work_slow_percent` of its median. For "how did the week go?" or "which step fails most?", run `careerbrew day history --json`.
10. `watch`: after the steps, keep one watch loop: `careerbrew day loop pass`, re-armed at the `next pass at` time it prints (or `careerbrew day loop run` in its own session). Never start a step's own watch phase or a second timer. A pass that says `skipped: previous cycle running` needs nothing. Record every cron, monitor, background agent, or session you start with `careerbrew day loop add --kind <kind> --id <id> --step <step>`.
11. `end_of_day` and `wrap_up`: wrap-up starts by clock at `wrap_up.at`. The watch pass writes tomorrow's handoff (open PRs and open questions, each with its recheck) and reminds the user once; keep the loop running and add only what you alone know (`careerbrew day handoff add`). When the user says "end of day", or the pass says `end of day by clock`, run `careerbrew day end`: it reads careerbrew's PM draft (never sent), writes the handoff, stops careerbrew's loops, and renders the page. Show its output and the Dashboard link. Write no Today / Tomorrow report of your own: the PM draft is the day's update. Stop each loop it lists with its own tool, then `careerbrew day loop stop --id <id>`, until `careerbrew day loop end` exits 0. `careerbrew day end` runs once a day: a second call changes nothing and says when the day ended. The clock ends the day only on a watch pass that day: a Mac asleep from wrap-up through midnight skips that day's end, so run `careerbrew day end` yourself when the user comes back that evening.
12. The next morning, `careerbrew day start` reruns each handoff item's recheck and drops the closed ones. Tell the user the open items in one line each.

Before reading the day plan, run `careerbrew day start --update-only --json`. On `updated: true`, re-read `$(careerbrew where)/commands/work.md`, this skill, and the changed plugin step files. Continue from the updated text. A failed refresh or repair blocks affected work; preserve dirty or diverged checkouts and report the next repair. Only then run `careerbrew day run --json` and `careerbrew day start`. The start preflight checks the installed /work, its non-code-block paths, legacy Agentfile steps missing from the plan, and every planned step file. Preserve owner edits before source sync; never delete an edited installed command.

After the first-turn source refresh and reload, at each turn start, including goal-hook turns, run `careerbrew day loop catch-up --json` before other work. It claims a stored pass or wrap-up more than 5 minutes late and runs it once through the normal pass lock. If a pass fails, pull its required sources again and retry through the normal loop. Do not wait for idle-session cron delivery. The host supplies `CAREERBREW_GOAL_ACTIVE=1` to preflight only while it knows its goal hook is active; absence means unknown.

The user can move today’s wrap-up with `careerbrew day wrap --at HH:MM` (the clock end moves by the same amount), or pause automatic wrap-up and ending with `careerbrew day wrap --hold`. `--at` resumes it; both the moved wrap-up and end must stay before midnight because records are day-scoped. For later work, hold it and explicitly end when ready. An explicit `careerbrew day end` ends now even while held. At wrap-up send each project session one graceful note: finish its current step, save work, update drafts, write its handoff, then report. Keep it running until that report arrives. The core records each request and refuses to archive a session until its handoff timestamp is newer than the request. Read the report before `careerbrew work session end <id>`. Repeated day end calls keep listing sessions that have not finished.

## Project sessions

The main session runs only the work process: stages, rows, the watch loop, and the one batched ask. Project work goes to project sessions, so project detail stays out of the main session's context (issue #274; the plan's `sessions` field).

Before selecting or dispatching project work, read `careerbrew work project list --json`. Skip a project while its `quiet` field is true, even if it has an open PM promise. Report that promise as deferred, not done. Do not send new project work or owner questions during the quiet period. If a session is already running, have it save its handoff and stop starting work. On the return date, use the saved project handoff as the brief. Set the date with `careerbrew work project set <name> --quiet-until YYYY-MM-DD`; use `--quiet-until none` to clear it.

Agent-provider gate: before you read work data with your own tools, follow rule 1 of `careerbrew-best-practices`.

1. Read `pm_promises` in the day plan first. If `needs_recording` is true, run `careerbrew day start` and read the plan again before selecting sessions. For an item marked `decision-needs-review`, ask the owner to review the listed decisions; do not start its session. When `missing` is true, read the last workday’s sent PM update with an authorized chat tool and record it with `careerbrew day pm-sent`; do not invent it. Cover the other open Tomorrow promises before ranked or stale projects, counting these sessions first against `work_session_cap`. Reuse a matched project’s live session; use an unmatched promise’s `session_project` so it gets its own session. In today’s PM draft, report each prior promise as done, moved, or still open with its reason; never silently drop one.

   Review proposals with `careerbrew work promise outcomes --json`. Only the owner can accept a current proposal with `careerbrew work promise accept <id> --yes`; never infer approval. For `decision-needs-review`, show the prior and current state and dates. Ask the owner to choose a listed keep, reopen, or drop id; keep restores the prior decision and reopen uses the original due date. If a choice also creates or keeps a separate promise, show that consequence and its due date before confirmation. Use `careerbrew work promise stats --days 7 --json` for aggregate outcomes. Missing receipts, invalid records, and ambiguous matches do not authorize a decision.

   Give each pressing project one long-lived session, reused all day. Before you start one, run `careerbrew work session open <project> --id <session id>` (the tool's own id). It records the session as a `session` loop, refuses a second session for the project, and refuses one past `work_session_cap`. Later the same day, `careerbrew work session open <project>` returns the live one: send the project's new work to it.
2. At the start of each project-session pass, read its current standing rules with `careerbrew work project rules <project>`. The read is a snapshot; an update during the pass appears on the next read. If business-data policy refuses the read, do not infer or bypass the rules; block that project's pass and continue independent work. Deliver the project's tasks one at a time, in order. Read each task's full scope in its ticket or issue, not only the brief. Finish every scope item, shipped and verified, before the next task. A plan, a dry run, or a list of questions alone is not delivery. Stop only at done or an explicit blocker: an operator-only decision or approval, or an outside wait. Batch foreseeable approvals up front, record each blocker with `careerbrew work session ask`, and continue independent work. Report each task with each scope item marked done or not done, with its verification or blocker.

   After each subtask, state the goal status in one line and start or name the next goal step. When replying to the owner, end with ranked next steps they can approve or pick now. If no owner action is needed, say so and name the next autonomous step; do not invent an ask.

   Before ending a turn, watch each external wait (such as CI, a judge, a reviewer, or a background job). Use a real PR monitor, scheduled wakeup, or the existing work-day loop with a recheck that covers that wait. Record any new loop with `careerbrew day loop add`; do not start a second work-day timer. Continue independent work while it waits. If the host cannot register a watch, say the wait is unwatched and why; do not claim a watch exists. Only stop watching when the work is done, blocked on the owner, or the work day ends.

   Give the session this contract. It writes through careerbrew, never through notes or a long report back:
   - each step: `careerbrew work agent event <agent> "<one line>" --session <id>` (Work's Agent activity shows it under the project);
   - each project change: `careerbrew work project update <project> <kind> "<one line>"`;
   - an approval note: `careerbrew work project update <project> approval "<one line>"`. The bounded note is not proof of approval for a PR's current head;
   - each question: `careerbrew work session ask <id> "<the ask>" --option <a> --pick <a> --recheck <check>`. A session never asks the user.
3. Claims: before a session writes a shared thread or draft, it runs `careerbrew work claim take slack-draft:<target> --session <id>`. Exit 1 means another session holds it: skip it and go on. Save the draft with `careerbrew draft replace <target> --file <file> --session <id>`, and release the claim when done (`careerbrew work claim release ...`). A claim lapses after `work_claim_minutes`. Before a project session works on a GitHub PR, use `careerbrew work claim take pr:<owner>/<repo>#<number> --session <id>`. Skip a held claim.
4. Read every session with `careerbrew work session list --json` (state, last event, claims, open questions, handoff). Their questions are in your one batched ask (`careerbrew day question recheck`).
5. End of day: first send the graceful wrap-up note and wait for the current step and fresh report. Then each session writes its project's handoff, `careerbrew work session handoff <id> "<where it stands; the next step>"`. Then run `careerbrew work session end --all` until it exits 0: it archives each session and releases its claims.

## Reply drafts

A step that drafts a chat reply follows the content and save rules (issue #269):

1. Read the thread to its newest message first. Write it to a temp JSON file (`{"messages": [{"ts", "text", "mine"}]}`) and run `careerbrew draft fit --thread <file> --draft <your draft file> --seen <ts of the newest message you read> --json`. It prints no thread text.
2. Follow `kind`: `none` (your message is the newest: no reply), `emoji` (suggest the `emoji` reaction, no text draft), `ack` (a release started: use `text`, or keep your draft when `keep_draft` is true), `stop` (only when you passed `--major "<one line>"` for an issue that must stop the release), `reply` (write or keep your reply). When `stale` is true, re-read the newer messages and redraft.
3. Save every draft with `careerbrew draft replace <target> --file <file>`. This saves only in careerbrew, not the chat tool. When a chat-tool draft is needed, save it there separately, read it back there, and run `careerbrew draft check --sent <file> --read-back <file>`. Exit 1 means the target holds other text: tell the user before anyone sends.
4. A step that writes drafts declares `uses: slack-draft:<target>`, so two such steps never run in one stage. A draft stays a draft until the user says send.

### Access blockers (issue #314)

A message blocked on a missing permission, policy, role, or group is work to resolve, also when it blocks a teammate:

1. Write the message to a file and run `careerbrew draft route --ask <file> --directory <channels.json> [--teammate <member id>] --json`. The directory lists each support channel (`id`, `owns` topic words, `members`) and its open `threads` (`channel`, `url`, `text`); build it from the chat tool's channel search.
2. Follow `action`: `link` (an open thread already asks it: reply there or link it, never open a second one), `open` (draft the ask in the owning `channel`), `unknown` (no channel owns the topic: find the owning team, add it to the directory, run it again), `none` (not an access ask). `tag` says to tag the teammate in the thread (a member) or to draft a reply in the original thread that links the new one.
3. Before any draft is saved, a fresh-context judge subagent reads the draft and the channel, and runs `careerbrew draft judge --draft <file> --channel <id> --directory <channels.json> [--new-thread]`. It fails a draft in a channel that does not own the topic, a new thread that duplicates an open one, and a mention of anyone not in the channel. Fix the draft and judge it again until it passes; only then `draft replace`. Never send.

With an empty work_steps setting, add steps for every day with `careerbrew config set work_steps "/standup, /review-prs"`. Before adding an owner step, read `careerbrew config` and retain the existing `work_steps` entries; update the same entry if it is already present. `config set` replaces the list. With an empty list, an owner command with ordering can use `careerbrew config set work_steps '[{"step":"/standup","scope":["work"],"after":["/refresh"]}]'`. A company plugin adds its own under `work_steps:` in its manifest, with `after`, `scope`, `uses`, and `longRunning` to say what may run at once (docs/plugins.md, "Work steps").

## Iterate

Append one dated line to `skills/careerbrew-work-day/LESSONS.md`: what worked, what failed, and why. If the behavior should change, update this skill and add a case in `evals/cases/`.

For an empty GitHub Authorization variable, first check source ownership. If agentbrew owns the connector, route the change to its registered source and sync; never ask to edit generated settings. For an owner-managed Claude connector, save one question explaining that `day start --fix --yes` will change Claude connector settings to use the existing gh sign-in at connection time. Never infer approval from the failed check. After the owner approves, run that repair, reconnect only with a tool the host actually exposes, and rerun preflight. A configuration-only success is not a verified connection: require a read-only GitHub MCP call through that client. If reconnect is unavailable or the helper is ignored, keep the manual recovery question. Tokens never go in chat.
