# Web app

careerbrew's main interface is a local web app. The CLI and agent skills stay for automation.

```bash
uv run careerbrew serve            # in a terminal, prints http://127.0.0.1:8765/#token=...
```

Or run `uv run careerbrew open [--view week | --report latest]`: it starts the app if needed and opens your default browser with the sign-in link, without printing the token. The token lasts across restarts (issue #141, [decision 0009](decisions/0009-web-token-lasts-across-restarts.md)): it is kept encrypted in `day/web-token.json`, reused by every start, and changed only by `careerbrew web rotate-token` (it signs out every open tab and bookmark at once; the web app's Actions view asks to confirm) or after `web_token_max_days` (default 30; the next `careerbrew open` makes a new one). The link carries it once as `#token=`; the app moves it into the tab's sessionStorage and sends it as a header. The tab then gets a sign-in cookie for 127.0.0.1 (HttpOnly, SameSite=Strict, one per port), so a reload, a new tab, or a bookmark of `http://127.0.0.1:<port>/` signs in by itself, also after a restart. A tab that cannot sign in (a new browser, a rotated or expired token) shows a sign-in page with the one command, `careerbrew open`, and an **Open a signed-in tab** button: the server opens the link in your default browser, and the old tab signs in again by itself. `careerbrew serve` prints the link with its token only in a terminal. Everything you typed (exercise drafts, PM drafts) is saved in the encrypted data folder, not in the tab. A start reuses the running app only when it answers to the token (`/api/ping`); `day/web.json` tracks its pid and port. A careerbrew server on the port that nothing tracks (left by a crash, a test run, or another data folder) is stopped and replaced, so the link always works; a program that is not `careerbrew serve` is never stopped, and the error names its pid. Starts take a lock (`day/web.lock`), so two at once share one server. Finding the server on the port needs `lsof`. The server listens on 127.0.0.1 only and checks the Host header. Every API route needs the token header; the cookie only gives the token back to careerbrew's own pages (`Sec-Fetch-Site: same-origin`), never to another site or to a page on another port of 127.0.0.1. Every response is `Cache-Control: no-store`, so your pages never land in the browser's disk cache, `frame-ancestors 'none'`, so no other site can embed the app, and `Cross-Origin-Resource-Policy: same-origin`, so no other page can load a response.

The sidebar has three groups: **Plan** (Dashboard, Teach me, Today, Standup, Notifications, Goals, Week, Work: your day, your goals, and your promotion case), **Job search** (Job hunt, Interviews, Practice, Library), and **System** (Review, Reports, Actions, Setup: careerbrew itself, how well it works, what its runs did, and how it runs). Each page starts with a one-line hint of what it is for. The groups live in `web/src/router.ts` (`VIEWS`).

On a corporate-role machine, Job hunt, Interviews, Practice, and Library answer 403. The app hides each blocked view from the sidebar, and a group whose every view is blocked (Job search) disappears; it never calls their endpoints, and a direct link shows why. The sidebar waits for the machine role (`/api/overview`) before it shows any group, so a blocked link never flashes and no group pops in and shifts the others. The rule lives in `web/src/router.ts` (`personalOnly`, `navGroups`).

## Design

Today and Standup share `feedHealth.tsx`. It reads uncached
`GET /api/feed/health`, shows distinct acquisition states and fixed CLI repairs,
and labels the saved row bundle's review age separately. Healthy direct coverage
does not pretend adapters are running. Today result ages use explicit canonical
source provenance, never an id prefix or event time. The browser-view timer uses
server-relative expiry, rechecks within one visible minute, pauses while hidden,
refreshes on visibility return and cleans up on unmount. It adds no clock to
`/api/changes` or the shared cache version. The real-clock synthetic test is
`web/e2e/live-source-health.spec.ts`; `feedHealth.test.tsx` covers state text,
visibility, expiry, retry and cleanup.

The layout borrows from the products people already use for each job, then trims them to what careerbrew needs:

| Pattern | Borrowed from | What careerbrew changes |
|---|---|---|
| Grouped sidebar (Plan, Job search, System), quiet neutrals, one accent | Linear | under 760 px it becomes one top bar with the brand and a **Menu** button that opens the grouped views; opening a view closes it |
| One agenda: meetings and planned tasks in one time-ordered list beside the day's numbers | Sunsama, Akiflow | the next step sits above it with the reason, so the list never has to be read to know what to do |
| Status-tinted job tables sorted by Want | Teal, Huntr | stages tinted by outcome (red for a "No:" stage, green for hired or offer); each posting links to its interview loop |
| Recall card: question, reveal, four grades with keys | Anki, Mochi | colour sits on the grade's edge, not the whole button, so Again is not alarming |
| Competency coverage with ranked gaps | brag-doc tools | each gap shows how to close it |

No web fonts and no CDN: the page loads nothing from the network. Light and dark follow the system setting.

**Main color: tangerine.** The owner chose it on 2026-10-27, after the Hallmark redesign moved the accent from indigo. It is `--accent` in `web/src/styles.css`: `oklch(72% 0.17 45)` in light and `oklch(77% 0.14 50)` in dark. A redesign keeps this hue. A hue change needs the owner's yes first.

The look follows the Hallmark design skill (task `hallmark-design`, 2026-10-27): its Furrow material, a field book of work records. Warm manila paper, near-black ink, one tangerine fill (with ink on it) for the primary action, the current view and the focus ring, and a grass green for what is on track. Links are ink with a tangerine underline; the accent is never text. The next step and the study card are notebook cards: an ink ring and a soft lift (in dark, a hairline ring and no shadow). Every colour, size, radius and gap is a token in the `:root` block of `web/src/styles.css` (one 4 px spacing scale, `--space-*`); dark re-derives the same tokens with the same hues. The stylesheet starts with the Hallmark stamp: its waivers and dismissals say why each kept finding stays. The audits are in [`docs/design/`](design/): run `/hallmark audit web/` again after a large style change and compare.

Every block says what it is (issue #147): a short "What is this?" line under its title opens one or two sentences. The answers live in `ABOUT` in `web/src/order.ts`, keyed by the block ids of `VIEW_BLOCKS`; `web/src/order.test.ts` fails when a block has none, and `web/e2e/inbox.spec.ts` opens every view and fails on a block without the line. An answer renders only while its line is open, so a folded line adds no words to the page.

### Comfort budget

Comfort browser contexts have test-fixture scope. `comfort-fixtures.ts` uses `comfort-screen.ts` to close only the contexts its own screen calls create, including body or new-page failure. The original viewport, media, permission and project options carry over. The final browser-only context-count probe records one numeric value and requires zero; it does not diagnose the original page stall.

Every view is built to a measured comfort budget (goal 2026-10-22, the `ui-ux-rankings` comfort patterns). `web/e2e/comfort.spec.ts` opens every view, a company page, and an action form on a phone (375 px) and a desktop (1280 px), in light and dark, with reduced motion, after the view has loaded and every `<details>` is open. It fails on:

| Check | Budget |
|---|---|
| Serious or critical axe problems (WCAG 2.2 AA) | 0 |
| Text under 14 px | 0 (body 15 px, card headings 16 px) |
| Touch targets under 44 px, on a phone | 0 (an inline link gets an invisible 44 px tap area that does not move the text; a link inside a sentence needs the height only, as WCAG 2.5.8 exempts it) |
| Text that spills out of its box (an id over a Week column, a number broken over two lines) | 0 |
| Raw ISO dates in app text (code, typed values, and imported notes excepted) | 0: a day reads "Wed Oct 21", another year's "Sun Jan 17, 2027" (`keepDates` in `web/src/text.tsx`, `friendlyDay` in `web/src/dates.ts`; a run page's heading too, `report._words`) |
| Pages that scroll sideways | 0 |
| Taps per everyday job, on a phone | open Today from another view 2, copy the PM update 1, show a flashcard's answer 1 |

Each run writes what it found and a screenshot per view to `test-results/comfort/<mode>/` (`found.json`). Before → after on 2026-10-22: axe 3 → 0, kinds of small text 212 → 0, phone targets under 44 px 1,115 → 0. A blind judge (a fresh agent with A/B screenshot pairs in random order, the key kept from it) preferred the new design on 32 of 36 screens; the two real losses (text spilling out of the Week columns, a number broken in Review) became the spill check, and its other findings were fixed: Library sections fold to their heading and count (a section with more than 10 pages starts folded unless you filter or it holds the open page), Setup's settings fold by topic (Work day open; each fold says how many you changed), Practice lists each topic in two lines, Standup folds the report file's path under "Also as a file", a Teach me card shows its question once (the block is "Recall this card"), a goal in another year shows its year ("Sun Jan 17, 2027"), and a run page puts Blockers first, then Next, then Done. Headings show friendly days ("Plan for Mon Oct 19", "Monday, Oct 19"), never an ISO date: use `shortDay` and `longDay` from `web/src/dates.ts`. A number drawn on a bar sits on a soft tint of the accent, so it keeps its contrast in both themes. A link inside running text is underlined, not told apart by colour alone.

Nothing scrolls sideways at any width (issue #67): not the page, and not any part of it. Long text (URLs, paths, ids, code) wraps. A table stacks into one block per row, each value beside its column name, when its box is narrower than 560 px; build every table with `DataTable` (`web/src/views.tsx`), which labels the cells. `web/e2e/app.spec.ts` ("fits its width") opens every view, a company page, a library page with code, and an action's output at 375, 768, and 1280 px, opens every `<details>`, and fails on any element whose content is wider than its box.

## Architecture

- `web/`: TypeScript, React 19, Vite. Hash routing (`#/dashboard` is the default, `#/today`, `#/interviews/<company>`). Typed client in `web/src/api.ts`.
- `src/careerbrew/server.py`: stdlib HTTP server, with a listen backlog of 128 so a page's parallel reads are never reset (the stdlib default of 5 was not). JSON endpoints `/api/session` (POST with the token header: sets the sign-in cookie; GET: the token back from that cookie, for careerbrew's own pages only) and POST `/api/session/open` (the sign-in page's button: opens a signed-in tab in the default browser; needs `Sec-Fetch-Site: same-origin`, never returns the token), `/api/ping` (`{ok: true, warm}` behind the token: a start checks the tracked server with it; `warm` is `done`, `busy`, or `off`, see the warmer below), `/api/tab-key` (the key the page encrypts its per-tab cache with; `null` with `web_tab_cache` off), `/api/focus/<block>` (one Dashboard block: `now`, `today`, `week`, `month`, `quarter`, `year`, `company`, `tomorrow`, `stale`), `/api/inbox` (careerbrew's open suggestions and questions, the fast part of the day log, with `groups` of alike suggestions and the suggestions hidden as done elsewhere, `expired`; `/api/daylog` carries the same three), `/api/checklist` (Getting started: each step, done or not, and whether Dashboard shows it), `/api/changes` (a content-free version over file names, inodes, sizes, and mtimes in `work/` and `day/`, without the watcher's bookkeeping `day/watch.json` and `day/cursors.json` (`CHANGE_SKIP`); the page polls it every 5 s while visible and refetches Today, Week, Dashboard, and the day log when it moves; reading a view or a watcher cycle that finds nothing new never moves it), `/api/overview|focus|feed/asks|daylog|daylog/<date>|standup|config|actions|notifications|today|week|jobs|interviews|interviews/<company>|cards|library|library/<id>|work|review|setup`, `/api/promises` (Dashboard's Commitments: open promises, overdue first; POST `/api/promises/<name>/done|dropped` closes one and returns the list), `/api/time-saved` (Dashboard's Time saved: `time_saved.compute()`, numbers and action ids only, never cached and never written), `/api/reports` (every kept run page's content-free summary) and `/api/reports/<id|latest|run>` (`{summary, html}`; any other name answers 404, so no path reaches the disk), and POST `/api/actions/<name>` (any action: `{values, confirm}`), `/api/notifications/<id>/read|accept|dismiss|snooze` (the same actions as a pop-up; returns the list), `/api/timing` (`{saves, step, seconds}`: one content-free `web.timing` event; anything else is 400; it keeps every cached view, since it changes no data), `/api/pm/send`, `/api/pm/draft` (`{day, text}`; empty text resets), `/api/inbox/<id>/accept|dismiss|answer|reopen`, `/api/inbox-group/<group>/accept|dismiss` (`{yes: true, ids}`, which the page sends only after you confirm, with the ids of the rows it showed; without either the answer is 400, and a row that joined the group since stays open, counted in `left`), `/api/config`, `/api/tasks`, `/api/tasks/<id>/done`, `/api/cards/<id>/review`, `/api/explanations/<id>/flag`, `/api/teach/complete`, `/api/teach/draft` (`{id, code}`: exercise code typed in the editor, saved to the encrypted `teach/drafts.json` so it survives a reload or restart), `/api/teach/feedback`, `/api/goals`, `/api/jobs/choose`, `/api/jobs/unchoose`, `/api/approvals/<id>/decide`, `/api/watch/<action>`. It serves `web/dist`.
- All logic and privacy guards stay in the tested Python core (ADR 0006).

## Develop

```bash
uv run careerbrew serve            # API on 8765
cd web && npm run dev              # Vite on 5173, proxies /api to 8765
npm run typecheck && npm run lint && npm test   # tsc, eslint, vitest
npx playwright test                # browser e2e over a synthetic data root (tests/e2e/web-seed-and-serve.sh)

## Controls and their tests

Every control works, and a test proves it (US-72). `web/e2e/controls.spec.ts` opens every view on a personal and a corporate machine, opens each folded part, shows each state the seed lacks (each teacher step, an edited PM draft, notifications off, the watcher on or paused, a refused clipboard, a block whose read failed, a signed-out tab, more suggestions than a page) by patching a GET answer, and lists every input, select, textarea, checkbox, button, button-styled link, and form by its accessible name. It waits until no block still shows its cached answer ("refreshing…"), so it lists the controls of the fresh one. It fails on a control with no name, a control with no entry in `web/e2e/controls.json`, an entry whose test does not exist, and an entry no view shows. `test-results/controls-<personal|corporate>.json` lists what it found and the test that covers each one. The sign-in page shows inside any view, so its controls are named `Sign-in page: …`.

To add a control:

1. Give it an accessible name: a button's text, or an `aria-label` or `<label>` on an input, select, or textarea.
2. Make it say something on every click: a button with nothing to act on yet is disabled (Add task with no title), and a failure shows an alert with a **Fix:** step (see Loading and errors).
3. Write a Playwright test in `web/e2e/` that uses the control and checks its real effect: the server's state read back through the API, the view after the server answered, or the error with its fix. A test that only sees it render is not enough. Set up the state it needs in the test; the suite shares one seeded server.
4. Add its entry to `web/e2e/controls.json`: `"<view>: <role> <name>": "<spec file> › <test title>"`. A test made in a loop is named as Playwright runs it (`blocks.spec.ts › Today: loading label at once, …` for `` `${v.name}: loading label at once, …` ``). Roles: `textbox`, `combobox` (select), `spinbutton` (number), `date`, `checkbox`, `button`, `link` (a link styled as a button), and `form` or `search`, named `submits "<its submit button>"`. Only a control made per row, action, or setting gets a pattern under `generated`, with its why.
5. If the control shows only in a state the seed does not have, add a visit to `VISITS` in `controls.spec.ts` that patches the GET answer (it never sends a POST to the server).
6. Run `npx playwright test e2e/controls.spec.ts` and the test you wrote; `npx playwright test` runs them all, as the gate does.

## Visual tests: approved pictures of every story's screens

US-75. Each user story with web views (its **Web views** line in `docs/user-stories.md`) has a visual test, `web/visual/us-NN-<slug>.spec.ts`. It opens the story's key screens and compares each one with its approved picture, `web/visual/__screenshots__/<spec>/<name>-<desktop|phone>-darwin.png`, pixel for pixel. `scripts/check-stories.py` fails when a story with web views has no spec, or a picture the spec names is missing at either width. ```bash
cd web && npm run build              # the server serves web/dist
npm run visual                       # compare every screen; writes nothing
```

What is fixed, so a picture changes only when the screen does (`web/playwright.visual.config.ts`, `web/visual/helpers.ts`):

- **Clock**: the server runs at `CAREERBREW_NOW=2026-10-19T09:00` (a Monday), and the browser's clock stands still at the same moment, both in Etc/GMT+4. The config fixes the day, whatever your shell exports.
- **Data**: the e2e seed (`tests/e2e/web-seed-and-serve.sh`, which runs every seed step in one process: `tests/e2e/web_seed.py`) on a fresh temporary data root, never your `private/`. A state the seed lacks is a GET answer patched in the page, never a write to the server, so the tests run side by side.
- **Screen**: desktop 1280 × 800 and phone 390 × 844 (touch), scale 1, light colours, en-US, reduced motion, no animations, no caret, and the pointer moved away.
- **Fonts**: the Mac system font, pinned in the picture's page, so a font installed on one Mac never moves a picture.
- **Saved Reports measurements**: only the visual config sets `CAREERBREW_VISUAL_SEED=1`. The seed pins watcher CPU history to 120 ms before saving the review report, matching the existing Review page fixture. Functional tests keep the measured CPU history and its 500 ms decision boundary.
- **Values that change on every run**: the watcher's CPU time on Review, the PM update's "updated" time (a file's write time), the standup page's path (a temporary folder), and the `stt_command` setting (the checkout's path to the fake speech-to-text script) are pinned in the page. Nothing is masked; `shot(target, name, { mask })` masks a part only when nothing can pin it.
- **Paths that differ per checkout or machine**: before each picture, `shot` fails when the page's text holds the checkout folder or the seed's temporary data folder, anywhere on the page, not only in the picture. A line with a path wraps differently in another worktree, and the line height (20.25 px) is not a whole pixel, so every block below it moves by part of a pixel and its picture comes out 1 px taller or shorter. Pin such a value with `patch()` in the `visual` fixture.
- **Live refresh**: `/api/changes` answers one version, so no refetch starts while a picture is taken.

Pictures are per platform: fonts render differently on Linux. On a platform with no pictures, the story says so and checks nothing.

2. `npm run visual:update` redraws the pictures that changed and writes missing ones. For one story: `npm run visual:update -- visual/us-NN-<slug>.spec.ts`.

## Speed: views answer a repeat from memory

Issue #117 (US-64). The server keeps the last response of each slow view in memory: Today, each Dashboard block (`/api/focus/<block>`, and `/api/focus` for the whole), open asks (`/api/feed/asks`), Week, the day log, Work, Job hunt, and Actions (`CACHED_VIEWS` in `src/careerbrew/server.py`). A repeat request answers from memory while its inputs are the same; the `X-Careerbrew-Cache` header says `hit` or `miss`.

- **Key**: a hash of the view and its query, the clock (the minute for views that count minutes: Today's next step, how long an ask waited, and the plans that start from the free time left today: Week, the day log, Tomorrow; the day for the rest), and a version of the whole data root (file names, inodes, sizes, and mtimes, without `logs/`). That version covers every folder `/api/changes` covers, so when the live views see new data on a poll, their refetch is a miss and shows it.
- **Expiry**: `web_cache_seconds` (default 300; `careerbrew config set web_cache_seconds 0` turns the cache off; a hand-edited value that is not a number counts as 300) bounds inputs that no file shows, such as calendar feeds read over the network.
- **Writes**: any POST clears every entry. Reading a view never writes a file that changed nothing: today's plan and the day log are written only when their content changes (`store.write_text_if_changed`), so a read does not move `/api/changes` and the live views do not refetch in a loop. A watcher cycle that finds nothing new moves no version either: the notification list, the project memory sync state, and the hourly change snapshot are written only when they change, and the watcher's state and checkpoints (`day/watch.json`, `day/cursors.json`), which every cycle rewrites, are left out of both versions (`server.CHANGE_SKIP`). No cached or live view may read a file on that list (test: `test_no_cached_or_live_view_reads_a_file_the_versions_skip`).
- **Not cached**: the watcher state (overview), keychain checks (Setup), the teacher's step timer, Review (it records history), Settings, the inbox (a fast file read), Getting started (`/api/checklist`: it reads the watcher state, which the change version skips, so the page reads it when Dashboard opens, not on each change), and `/api/changes`.
- **Warm** (issue #142): `careerbrew serve` starts a warmer thread (`server.Warmer`, server-instance scope). At start, and whenever the data version moves (a watcher cycle, the CLI, a plugin; it looks every 2 s), it builds the work views a page opens first (`WARM_VIEWS`: the day log, Today, open asks, Week of 7 days, Work, and every Dashboard block), so the first open after a start or after new data answers from memory too. The day log and Today go first: their first rebuild can write a file, which moves the version the others are keyed by. Views keyed by the minute (Today's next step, open asks, Week, the day log, the first four Dashboard blocks, and Tomorrow) stay warm until the minute changes. `/api/ping` says `warm: done` once every warm view is built for the current data. With `web_cache_seconds 0` it does nothing. Each warm logs a content-free `web.warm` event.
- **Dashboard blocks** (issue #142): the blocks a page asks for at once share one `focus.Build` (kept per minute and data version on the server's cache), which computes each shared input (the ranked tasks, the day and week plans, the ladder assessment) once, even for parallel requests.
- **Lifecycle**: one `ResponseCache` per server (server-instance scope); it holds one entry per view and query (at most 64, oldest out first) and goes away with the server. Two requests for the same view wait for one rebuild. Responses stay `Cache-Control: no-store`, so nothing lands in the browser's disk cache.
- **Measure**: `uv run python scripts/api-timing.py` seeds the e2e data root in a temp folder, waits for the start warm, and prints two requests per endpoint (`--check` fails when a cached view's second request is not a hit, a warm view's first open is not a hit at start or after new data (a CLI note and a watcher cycle), a read moved `/api/changes`, or an idle `careerbrew day watch once` moved it or cost a cached view its hit). On your own machine, `grep '"web.api"' private/logs/events.jsonl` gives `route`, `cached`, and `ms` per request.

## Blocks: loading, errors, the page's cache, and spacing

When the first live change check succeeds, open live blocks refresh once. This catches updates made while the page was opening. Later checks refresh them only when the version changes.

Issue #142 (US-58, US-64). A page is a stack of blocks, and each block loads, fails, and refreshes on its own (`State` in `web/src/views.tsx`, data from `useData` in `web/src/useData.ts`):

- **Loading**: a visible skeleton that says what it loads ("Loading the next step…"), plus the seconds once it takes 3 s or more. A page is never blank.
- **Errors**: a block that fails shows its own error with the fix (the same `explain` text as actions) and a **Retry** button; the other blocks stay. When a refresh fails, the block keeps its last data, marked "not refreshed".
- **Parallel blocks**: heavy views ask for their parts at once. The Dashboard asks for each horizon, Tomorrow, and the stale sources on their own (`/api/focus/<block>`). Today asks for the next step and plan (`/api/today`), the open asks, the day log, and the inbox (`/api/inbox`) at once; the inbox shows before the day log, which rebuilds the log.
- **The page's cache** (`web/src/cache.ts`): the last answer of each view's endpoint stays in the page's memory (browser-page scope), so a view switch shows it at once, and in the tab's `sessionStorage` (tab scope), so a reload does too. The block shows it with "Updated hh:mm · refreshing…" and replaces it when the fresh answer arrives (stale-while-revalidate). When `/api/changes` moves, every cached answer is marked stale ("new data, refreshing…"). The tab's copy is encrypted (AES-GCM) with a key that only the running server holds in memory (`/api/tab-key`); entry names are hashes, so the endpoint (a company or page name) is not readable either. The browser may keep `sessionStorage` on disk to restore a session; without the server's key that copy cannot be read, and a restarted server's new key drops it. The token is never in it. When the `/api/tab-key` call fails (a 401 right after `careerbrew web rotate-token`), the page keeps the cache in memory and asks for the key again on its next read, so after a fresh sign-in the tab's copy works again without a reload. `careerbrew config set web_tab_cache false` keeps the cache in memory only, and the page asks for the key only once.
- **Forms in a cached block** keep what you type when the fresh answer (or a live refresh) replaces the cached one. A form is never keyed on freshness or on a value each read changes, so it does not mount again: the Goals form takes the fresh lists and keeps the goal you are typing (an edit stays on its goal, found by id, or becomes a new goal when that goal was removed elsewhere), so a save never drops a goal added elsewhere; a Teach me step is keyed on what it is (`stepId`), not on the `started` time the server stamps on every read; the PM update box takes a new draft only while it holds no unsaved typing. Settings, Week's new task, and the other forms keep their state outside the cached block.
- **Spacing**: one token, `--space-4` (16 px), is the gap between every stacked card, grid row, and column (`.stack`, `.grid`, `.split`, `.columns`); every view sits in one `.stack`, so no two blocks touch.
- **Tests**: `web/e2e/blocks.spec.ts` (run by `tests/e2e/us-58-action-feedback.sh`) opens every view with its reads held and checks a visible loading label within 100 ms, then fails them and checks an error with Retry, retries, checks a gap of at least 8 px between neighbouring cards, then reloads with every read held and checks the cached data and its "Updated" note. On Dashboard and Today it holds one block's read and checks that the other blocks show their data meanwhile, then fails it and checks that only that block shows the error and Retry loads it. It also moves `/api/changes` while a view is closed and checks that switching back says "new data, refreshing…". Unit tests: `web/src/blocks.test.tsx` (the block states, the stale note after `/api/changes` moved, and the encrypted tab copy), `web/src/cache.test.ts` (a failed tab-key call is asked again; an off answer is not), `tests/unit/test_web_blocks.py` (block endpoints, the shared build, the tab key, the warmer). Typed text across the swap: `web/src/teach.test.tsx` (Goals and a Teach me step), `web/src/daylog.test.tsx` (the PM update box), and `web/e2e/inputs.spec.ts` "Goals: a title typed while the view shows its last answer…", which holds the fresh read while it types.

## Loading and errors

The Copy update and PM update blocks expose a content-free `data-daylog-fresh` state for their current loader. It is true only after that loader's fresh request succeeds; pending, cached, failed, and superseded loads are not fresh. The source-health expiry story waits for these states and the observed setup requests before its baseline, then still checks for later writes (`health-setup.spec.ts`, `live-source-health.spec.ts`).

Every form, button, and inline answer shows a "working" note (Saving…, Sending…, Adding…, Running…) and disables its button while the request runs. When it fails, an alert shows the server's message and a **Fix:** step: start careerbrew (`uv run careerbrew`) when the server does not answer, reopen the link (`uv run careerbrew open`) on 401, see Setup on 403, reload on 404, check the input on other 4xx, and check the server log or `scripts/doctor.sh` on 5xx. What you typed stays in the box. A block whose data fails to load shows the same alert, with Retry (see Blocks above). A button with nothing to act on yet (Add task with no title, Open loop with no company, a long-term goal's Add with nothing typed) is disabled, so no click does nothing. The shared pieces are `web/src/act.ts` (`useAct`, `explain`) and `web/src/act-status.tsx`; `web/e2e/feedback.spec.ts` checks both states in every view.

## Bad input

The API returns 400 with an `error` message for bad input: a bad due date, hours that are not a number from 0.05 to 200 (NaN and Infinity included), a non-number `days`, a body that is not a JSON object, deeply nested JSON, or a bad `Content-Length`. An unknown task id answers 404. Responses are strict JSON: a non-finite number is sent as `null`. It never drops the connection.

## Test resources

Web unit tests use one to two file workers, clamped to available CPU parallelism.
The Node-only Vite config uses the development-only `@types/node` declarations
for its built-in CPU query. This bounds the test process pool; it does not change application behavior,
assertions or waits. Vitest CLI worker options still override the default. Run
`cd web && npm test -- --run` normally. For the full gate on this Mac, use
`UNIT_JOBS=2 E2E_JOBS=2 CHECK_EVALS=1 heavy-run scripts/check.sh` from the repo root. The
E2E runner default is unchanged.

Source notices explain that recent work may be missing and give a plain request
to Claude for setup, restart, or refresh. Technical repair commands stay in the
health API for agents; the notice asks for no file path.

For a local comparison, `CAREERBREW_BROWSER_RECEIPT` may name a new private file. It holds test and project identifiers, so keep it local. The file records the identity comparison only; keep the story exit status as separate evidence. A failed write does not publish a partial receipt.
