# Privacy

This repo is safe to push. careerbrew itself keeps personal and business data out of git, logs, and plain-text backups. It sends such data to a hosted model only on a route marked `private_data: true`. It prints such data for an agent only in the cases the exits table names (personal files; business text when a plugin policy allows it). Every exit and its guard is in [Data exits and their guards](#data-exits-and-their-guards).

Anything an agent reads with its own tools (work chat, tickets, mail, links, internal docs) goes to that agent's provider. Use those agent flows (the live feed, the work companion, promotion research on an internal ladder) only when your employer approved that provider for that data. For model calls on a corporate-role machine, careerbrew itself sends business data only to a model route on that machine. A message you send yourself (a PM update to your company Slack, on your click) goes to that tool. On a personal machine, a command that writes with a model (for example the promotion doc) may send your evidence to a hosted route marked `private_data: true`. The plugin policy field `agent_may_read_business` (default `false`) limits what careerbrew itself shows or writes for an agent (command output, watcher research, project memory notes); it does not limit the agent's own tools. One case to know: when you run a command in your own terminal or the web app, careerbrew writes work notes (titles and links) into the project's memory file even with the field off. An agent that reads that file sees them, and so does its provider.

`.gitignore` is an allowlist: only the paths it lists can be committed.

Sent PM text and its receipt use one canonical sent-day lock at
`private/day/.pm-sent-<day>.lock` under the configured data root. Saves,
source/receipt reads and learning share this lock, released on every exit.
The empty file remains after unlock and holds no message text or receipt
identity. A preview may create this control bookkeeping file, but does not
rewrite business records, receipts or promise metadata.
The API input version ignores only empty canonical sent-day locks directly in
`day/`, using filename and size metadata. Nonempty locks, near-name files,
locks elsewhere, sent text and receipts remain version inputs. No lock content
is read or copied into the cache key.

Live-source validation receipts have data-root lifecycle in encrypted
`work/live/state.json`, owned by `work/live.py` under its existing cycle lock.
They contain source/config digests, content/stat fingerprints and acquisition,
acceptance and check times; never raw replies or configuration paths. Cycle
records add health, age, unchanged flags, payload-validation times and final
health-as-of times. Final evaluation never creates or renews a receipt. Polling never renews acquisition.
The receipt remains until replacement or data-root removal; stopping keeps it.

## Data exits and their guards

Source-health GETs read existing encrypted declarations and validation receipts.
Their versioned output contains canonical source ids, finite reasons, times,
ages, counts and fixed existing repair commands, never titles, raw replies,
configured pull commands, credentials or arbitrary paths. Direct completion
state has data-root lifecycle in `work/feed/direct-cycle.json`; the live cycle
lock owns its writes. Pending batch metadata stays under the feed lock and is
released before completion/publication. Receipts and source payloads remain
encrypted. Eligible direct results retain canonical source provenance; this
does not certify old row facts or proofs. See [coverage and source health](integrations.md#direct-coverage-and-source-health).

## Sensitive terms

careerbrew blocks these from every exit:
- the `name`, `employer`, `email`, and `sensitive:` entries in `private/profile.yaml`;
- each line of `private/sensitive-terms.txt`;
- each installed plugin's `sensitive_terms` file.

## Rules for agents

Task proposal replies include their opaque inbox id and exact owner accept
command. Restricted inbox output also permits canonical ASCII task references
matching `t[0-9]+`. It never prints an arbitrary legacy reference, title,
reason or link. The offer receipt has invocation scope and contains only the
inbox id and `new`, `updated` or `decided` status (`test_issue_371.py`).

1. Read and write personal data only under `private/`. Never copy it into a commit, a test, a log line, an issue, a PR, or memory.
2. Learn about business data from CLI output (aggregates, ids, paths, and a file's structure from `careerbrew data show <file> --keys`), not by opening `private/work/` or `private/out/promo-*` files. That is unless the active plugin policy sets `agent_may_read_business: true`, which means the company has approved your AI provider.
3. Tests and evals use synthetic data with canary strings only (`CANARY-PERSON-7Q`, `CANARY-EMPLOYER-3X`, `PROJECTZEBRA`).
4. Never add a hosted route with `private_data: true` unless the user accepts that provider's data terms in writing (an ADR).

## Backups

`careerbrew backup create` writes an encrypted, verified archive of `private/` (minus the cache) to every target in `private/settings.yaml` (default `~/Backups/careerbrew`), and keeps the last 10. Point a second target at an external drive, or at a synced drive on a personal machine only (a corporate machine refuses a cloud-synced target). Store the key in your password manager. Test a restore once: `careerbrew backup restore <file> /tmp/restore-test`.

Out of careerbrew's control: company-managed Time Machine or MDM backups of the corporate machine. They are the company's own infrastructure; ask IT whether they cover the data folder.

`data set profile.yaml` changes only the supplied name and employer fields.
Its CLI output, event, and web action result omit the values. The web request
still carries them locally. Command-line arguments can appear in local process
listings and shell history, so do not use this action for secrets. Concurrent
`data set` calls share a lock; other profile writers do not. The action preserves
comments and refuses YAML anchors, duplicate keys, and complex target fields;
use the editor for those files.

## Agent deployment metadata

Careerbrew's data-root `agentbrew/Agentfile.yaml` is private plaintext configuration
metadata (source file paths only, mode 600 under a mode-700 folder), so agentbrew
can consume it. It contains no career records or credentials. Each write uses a
unique mode-600 `.tmp` sibling, excluded from bulk vault scans, and publishes it
after closing the writer. Before cleanup, the writer checks the temporary file identity; if it does not
match or is unknown, the path is left for inspection. The identity and directory
checks are not atomic with later path operations: another process using the same
account can replace a path between them. This does not serialize the later
agentbrew read. Canonical private
plugin workflows remain the only command source; generated agent files are outputs.
Legacy plugin-owned command archives and their restore receipts use the encrypted
store. A leaf is removed only after old-source byte equality and read-back
verification of both archive and receipt. Owner edits or an unavailable prior
source stop migration without deleting the leaf. Tests isolate the external
deployer in scratch environments and never sync into the owner's configuration.

### Approved GitHub connector repair

`day start --fix --yes` changes only an approved Claude GitHub header configuration. It follows the configured symlink and atomically replaces its real target with the original mode, preserving other fields. A resolved-config-target lock serializes repairs; the OS releases it on exit and the empty lock file stays for future writes. A temporary sibling file is removed on failure. A source change detected by the final byte/metadata check aborts the write; other clients do not share the repair lock. No new credential is fetched, printed, or stored by the repair. The client later runs the helper and receives its JSON header privately; helper failures print no credential or error payload. CLI and Actions output contain counts and configuration-only verification. Tests use fake gh and temporary client settings.

## Migration action capture

The developer command `cargo xtask migration capture-actions` runs Python
action discovery twice in fresh synthetic homes. Each receipt includes
the observed command, output, status, loader paths, dependency and source
hashes, and retained changes under the owned roots. Receipt files contain
local machine paths and stay local under `.metrics/`. The capture scans
retained content before hashing it. Transient writes and writes outside
the owned roots are not observed. The pinned Python startup hook is
migration-oracle instrumentation and retires with that oracle.

The developer command `cargo xtask migration capture-http` captures the real
Python HTTP handlers in two fresh synthetic homes. Its pinned fixture driver
starts `make_server` on a loopback port. It does not run CLI startup or the
warmer. Actual request/response bytes, synthetic cookie tokens, handler PID
and source/dependency paths remain in local receipts under `.metrics/`. The
first preserved candidate is marked `reference-review-pending`. Later
captures must match its reviewed, checksum-pinned HTTP projection. Agreement
between two fresh runs alone does not qualify the contract. The receipt
separates HEAD identity from hashes of the actual implementation files. The same invocation-owned child guard
closes and reaps the driver. Retained owned-write snapshots do not observe
transient/outside writes or descendants that escape its process group.

Readiness metadata has capture-invocation scope. The driver writes it to an
exclusively created sibling temporary file, closes the file, then atomically
renames it to the final path. A paused real write tests that readers cannot
see a partial final file. A separate fully closed malformed publication must
still fail immediately; the reader does not retry malformed JSON. These checks
do not establish crash durability or complete filesystem observation.

## Browser test cleanup diagnostics

A repair-fixture invocation can emit one content-free JSON line to test stderr
before rejecting an EPERM process-snapshot fallback. It contains only numeric
process/group/user ids, bounded known process-state flags, fixed classifications,
whitelisted ps status fields, and the worker Node version and numeric device and
inode of the file at its executable path. The file metadata is observed after
startup and does not prove the running image was not replaced. It excludes paths,
arguments, environment, raw ps stderr and malformed row text. The projection keeps at most 128 general rows
and 128 owned-group rows, with explicit truncation and a 32 KiB output bound.
The original cleanup decision still scans every row and throws the same error.
Test logs remain local; no production telemetry or additional process owner is
added. Synthetic refusal and canary controls are in `test_mcp_browser_fixture.py`.

## Migration DATA capture

The developer command `cargo xtask migration capture-data` uses fresh synthetic
homes and the existing shared child owner. Its fixed Python API observations,
source/runtime pins and typed cleanup records stay in new local `.metrics/`
receipts and raw sidecars. No owner career data or production Rust route is used.
Canary checks and protocol admission apply before retaining diagnostic content.
The fixed corpus observes retained invocation-owned writes; it does not observe
all transient or outside writes.


The developer command `cargo xtask migration observer-probe` runs only its fixed
synthetic Linux/arm64 process tree in an invocation-owned Docker container.
Docker calls use an empty owned client configuration, an explicit local Unix
socket and a cleared environment. The image is immutable and has no owner
mounts or outside network. Raw syscall traces, fixed public marker bytes,
process results, local paths and image/source identities stay under the new
local output directory. The two client-failure controls also use only owned
synthetic containers. Raw files are copied while the supervisor keeps tmpfs
alive, before release and exact owned-resource cleanup. This fixed capability
probe does not qualify whole-application tracing, general path resolution,
outside writes, CPU/RSS accounting or other platforms.

Fixed observer tmpfs export uses the pinned supervisor and bounded Docker exec
reads. Its temporary Python exporter remains a migration oracle. Manifests
contain allowlisted file identities, sizes and hashes; byte chunks stay in the
owned local snapshot. Command receipts keep chunk byte counts and hashes, not
duplicate raw chunk payloads. No owner data, host mounts, network route, new
process owner or larger shared stream limit is added. Snapshot files have
invocation scope and remain local with the run evidence until explicit cleanup.

## Sent PM coverage audit

The local audit requires a foreground owner terminal or the business-read
policy. It reads shown drafts, sent sources and history through the encrypted
store. It returns aggregate counts and a rate. It creates no key, lock,
history row or event and makes no network request.

The output also contains aggregate missing, stale, matching-body-elsewhere
and duplicate-day counts. A body match elsewhere does not disclose its date
or prove that a record was misdated. Incomplete observations discard every
count. Existing coordination locks are opened read-only and nonblocking;
the audit never creates missing locks or keys. Synthetic tests snapshot data
files, directories and the external key, including bytes, modes and modification
times. These retained snapshots do not measure filesystem access times.

### Git pre-push context

The pre-push hook checks bounded Git ref-record syntax, runs the strict leak scan, and then gitleaks. It runs no test: the hosted checks do ([ci.md](ci.md)). An empty record stream is valid for an up-to-date push and still runs the scan. It also stops a push whose history is not only the public history (an old checkout, a merge of both histories, a tag of a tree), and names `docs/migrate-to-public-history.md` (test: `test_pre_push_root_guard.py`). This check does not verify the remote target or scan pushed history for content; it grants no privacy exception. Remote arguments are not printed by the hook.
